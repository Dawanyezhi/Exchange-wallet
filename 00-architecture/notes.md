# 00 - 架构深度技术笔记

## 为什么密钥层和钱包层要分离

### 最小权限原则
钱包服务需要的不是"主种子"，而是"当前交易的签名结果"。
通过分层架构：
- walletmanager 持有主种子（root.json），按需派生子密钥，在内部完成签名后返回签名结果，私钥从不离开 walletmanager 进程
- 钱包服务只发送原始交易数据，拿回签名，自己从不接触私钥
- walletmanager 内存中同时存在的私钥最多几十个（并发签名请求各自派生一个，签完立刻四步清零）
- 即使钱包服务整个进程被攻破，攻击者也拿不到任何私钥，更无法派生任意地址的密钥

### 稳定性隔离
密钥服务的网络策略极严格（通常只允许来自特定钱包服务 IP 的请求），
如果密钥服务和钱包业务在同一进程，一个 bug 导致重启就会重新拉取所有私钥，
增加私钥在内存中的暴露时间。

### 审计面
独立进程 = 独立日志 = 精确审计每次私钥分发。
混在一起时，私钥访问日志会淹没在大量业务日志中。

## 三种链类型的核心差异

### Account 型（ETH/BSC）
- 地址在所有交易中复用（充值地址固定）
- 余额是账户状态（一个 mapping: address → balance），不是 UTXO 集
- **Nonce** 防重放：每笔交易的 Nonce 必须严格递增，跳号会导致后续交易全部堵塞
- 重组回滚：只需回滚余额变更记录，不需要恢复 UTXO 集

### UTXO 型（BTC/LTC）
- 每笔交易消耗若干 UTXO，产生新的 UTXO
- 无 Nonce 概念，交易之间没有显式的顺序依赖
- **重组回滚的额外步骤**：被该块"花费"的 UTXO，需要从 Spent 状态恢复为 Available
  - 如果漏做这步，那些 UTXO 会永久"消失"，用户余额凭空减少
- 归集时需要 UTXO 选择算法（最优找零）

### Tag 型（XRP/XLM）
- 交易所只有一个地址，通过 Memo/Tag 区分不同用户
- **Memo 丢失是最常见的用户投诉**：用户忘记填 Memo，资金到账但系统无法归属
- 充值处理：必须校验 Memo 是否在已分配列表中，忽略无 Memo 或无效 Memo 的充值
- 归集：不需要，因为资金已经在交易所的地址上

## 确认数（SafeHeight）与重组防护

### 为什么需要确认数

区块链会发生**重组（Reorg）**——两个节点几乎同时出块，网络短暂出现两条并行链，最终选择最长链作为主链，另一条上的区块被废弃，那些交易"从未发生过"。

```
正常：  ... → 990 → 991 → 992 → 993（主链继续）

重组：  ... → 990 → 991' → 992'           ← 废弃链（交易消失）
                   → 991  → 992 → 993 → 994  ← 主链（更长，胜出）
```

对交易所的具体威胁：**假充值双花**

```
1. 攻击者向交易所充值 10,000 USDT（块高 991）
2. 交易所确认数不足，直接上账并允许提现
3. 攻击者提走 10,000 USDT
4. 发生重组，块 991 被废弃 → 充值"从未发生"
5. 攻击者白拿 10,000 USDT，充值的钱仍在自己钱包
```

**确认数就是解法**：等块高足够深（重组不可能延伸到那里）再上账，把这个风险窗口关掉。

---

### SafeHeight：确认数的工程实现

```
当前最高块：1000
确认数配置：12（ETH）

SafeHeight = 1000 - 12 = 988

Front = SafeHeight = 988   ← 此高度以下可上账、可归集
Back  = 当前最高块 = 1000  ← 已扫描的最新块
```

- 高度 ≤ 988：确认充分，可上账和归集
- 高度 > 988：还在窗口内，不可上账（重组仍可能撤销）

滑动窗口：新块到来时 Front 和 Back 同步向前推进，窗口内保存区块头用于 parentHash 重组检测。

### 各链重组概率与确认数配置

| 链 | 确认数 | 重组概率 | 原因 |
|---|---|---|---|
| ETH | 12 | 极低，偶发 1-2 块 | PoS Finality Checkpoint，2 个 epoch 后不可逆 |
| BSC | 20 | 低，偶发 1-3 块 | 21 个验证者 DPoS，出块快但偶有短暂分叉 |
| Polygon | 400 | 中，历史最深约 400 块 | 2023 年 BOR+Heimdall 双层共识窗口期导致深度分叉 |
| ETC | 500 | 高，历史最深 3693 块 | PoW 算力低，2020 年三次 51% 攻击 |

**ETH epoch 是什么：**

```
1 slot  = 12 秒（一个出块机会）
1 epoch = 32 slots = 32 × 12s = 384 秒 ≈ 6.4 分钟
2 epoch ≈ 12.8 分钟
```

ETH PoS 用 Casper FFG 做最终确定性：每个 epoch 结束时，验证者对"检查点"投票。连续两个 epoch 的检查点都被 2/3 以上验证者投票通过后，该检查点进入 **Finalized** 状态。

Finalized 之后要回滚，需要至少 1/3 的质押 ETH（数百亿美元）被罚没（slash）——经济成本极高，实际上不可能发生。

所以 ETH 确认数只需要 12 块（约 2.4 分钟 < 1 个 epoch），远小于 2 epoch，已经足够安全。

---

### 重组发生后必须回滚

SafeHeight 防的是"已上账数据被重组撤销"，但 SafeHeight 以上还未上账的区块仍可能被重组。检测到重组（parentHash 不匹配）就必须回滚，否则：

- **余额错乱**：DB 有充值记录，链上那笔交易已不存在，用户余额虚增
- **归集打水漂**：去归集一个"已充值"的地址，余额为 0，Gas 白费
- **对账永远对不上**：链上 vs 本地余额持续偏差，告警不断

原子回滚（源自 irwallet/repository/walletdb/internal/reverter.go，全成功或全失败）：

```
检测到重组（parentHash 不匹配）
  → 1. revertBalance    还原用户余额（减掉该块的充值 delta）
  → 2. revertInboundTx  DELETE inboundtx（删除充值记录）
  → 3. revertOutboundTx UPDATE outboundtx SET status=Pending（提现退回待确认）
  → 4. revertSystemTx   UPDATE systemtx  SET status=Pending（归集/补费退回）
  → 5. revertHeader     DELETE header（删除该高度的区块头）
  → 6. revertHeight     UPDATE height SET front=?, back=?（游标回退到重组点）
  → 7. revertUTXO       仅 UTXO 链：恢复被该块花费的 UTXO 状态（Account 链跳过）
  → callback()          外部钩子（告警、日志等）
  → Commit
重新从重组点扫块
```

步骤 1 在步骤 2 之前：余额从充值聚合而来，删记录前必须先把余额改回去，顺序不能颠倒。
